## Design goal

The executor must be able to place and cancel scoped maker orders while
making four bad outcomes structurally impossible, not merely forbidden:
(1) theft or loss of the operator's main funds, (2) spending beyond the
registered stage cap, (3) withdrawal of funds by the executor, (4) key
exposure via the repository, telemetry, chat, or backups.

## Recommended design: dedicated trading sub-account, cap by construction

1. A NEW Polymarket account ("executor account") is created by the owner,
   separate from the operator's existing account. Its wallet holds ONLY
   the current ladder-stage capital (Stage 1: $100). The cap is enforced
   by physics: the account cannot spend money it does not hold.
2. The operator's existing account (holder of main deposits) never has
   its credentials on any machine. Top-ups of the executor account are
   manual owner actions, sized by the frozen ladder only.
3. Credentials for the executor account:
   - The L1 private key is generated by the owner, used once to derive
     the L2 CLOB API credentials (key/secret/passphrase), then stored
     ONLY in the owner's offline password manager — never on the VPS.
     If order signing requires the key at runtime (EIP-712 maker
     orders), a dedicated signing key holding no withdrawable value
     beyond the stage cap is the accepted residual risk — that is
     exactly what the sub-account isolates.
   - Runtime credentials live ONLY in the VPS `.env` file (mode 600,
     owner-only), which is already outside the repo, outside telemetry
     whitelists, and outside the WO-65 archive. A pre-registered grep
     guard test asserts no credential-shaped string ever appears in any
     telemetry-whitelisted directory.
4. Scope of the credentials: trade + cancel only. No withdrawal
   capability is ever configured; funds leave the executor account only
   by the owner's manual action.
5. Rotation and revocation (tested BEFORE first live order):
   - Rotation: derive fresh L2 credentials, swap `.env`, restart the
     executor container; old credentials die with the derivation.
   - Revocation drill: kill the credentials mid-session and verify the
     executor fails flat (cancel-all attempted, then halt + alert),
     with the failure appended to the anchored execution ledger.
6. Interaction with existing controls: the dead-man switch, kill
   criteria, and WO-62 three-way reconciliation all run against the
   executor account's wallet. The reconciliation gains a second
   monitored address (executor account) alongside the operator account.

## Rejected alternatives (recorded so they are not re-litigated)

- Operator's main account credentials on the VPS: rejected — couples
  main funds to the automation blast radius.
- Credentials in GitHub secrets or repo-adjacent config: rejected —
  repository and CI surfaces are the most-audited, most-shared surfaces
  we have; keys do not belong on them.
- "Small enough not to matter" ad-hoc scripts with pasted keys:
  rejected permanently; violates the foundational invariant regardless
  of size.
